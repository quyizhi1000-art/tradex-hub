# 需求拆解、方案复核与执行确认

本 skill 仅在用户显式调用 `$requirement-plan-audit`（或在界面中选择本 skill）并要求方案审计时运行。不得因普通的实现、修改、修复、重构、咨询或只读请求自动应用本流程。

一旦被显式调用，把当前实施型需求视为“开始制定与审计方案”，而不是实施授权；完成本流程并取得最终确认后再实施。

## 工作边界

- 方案阶段可以读取仓库、配置、历史和现有测试，以事实支撑判断。
- 在用户批准最终方案前，不修改项目文件，不提交代码，不执行部署、迁移、外部写入或其他实施动作。
- 只分析当前需求，不借机扩大范围。明确区分已知事实、推断、假设和待确认项。
- 全程允许并鼓励自我质疑：可以撤回假设、推翻初稿、更换推荐方案。不得为了保持前后一致而维护已被证据否定的判断。

## 第一阶段：拆解需求

先检查与需求最相关的仓库内容，再输出：

1. 用户目标与预期价值。
2. 功能需求、非功能需求、约束、非目标和验收标准。
3. 受影响范围、依赖、边界条件和未知项。
4. 当前假设及其依据；标出会实质改变方案的待确认问题。
5. 合理性检查：矛盾、不可行点、不必要复杂度、安全或数据风险，以及需求与现状不一致之处。

若合理性检查发现必须改变目标、范围、行为或验收标准才能继续，提出具体的需求修改建议，说明原因、影响及保留原需求的后果，然后暂停并征求用户同意。未获同意不得把建议当作既定需求。仅需普通工程假设且风险较低时，可记录假设后继续。

## 第二阶段：形成待审方案

基于仓库事实和已确认的需求给出可执行方案。存在实质性取舍时比较候选方案，并说明推荐理由。待审方案至少包含：

- 总体思路及关键设计决策；
- 预计影响的模块、接口、数据或流程；
- 分步实施顺序与每步可验证结果；
- 测试与验证策略；
- 兼容性、迁移、回滚、性能、安全和运维影响中与本需求相关的部分；
- 风险、未知项、替代方案与置信度。

保持风险对称：只写与当前改动有关的检查和措施，不用模板化条目制造虚假的完备感。

## 第三阶段：自我复核并请求确认

主 agent 必须亲自核对待审方案与仓库证据，并进行一次反方复核：主动挑战需求理解、核心假设、推荐方案、可删减内容、被忽略的替代方案和最可能失败点。若证据支持，应撤回假设、推翻或重写原方案，不得为了维持前后一致而保留较差方案。

向用户提交自包含的最终结果：

1. 最终需求理解与已确认假设。
2. 最终推荐方案和实施步骤。
3. 自我复核发现的主要问题，以及方案因此发生的修改。
4. 未采纳的替代方案及理由。
5. 风险、验证、回滚和仍需用户决定的事项。
6. 明确说明此时尚未执行任何实施改动，并询问用户是否批准按最终方案执行。

只有用户在看到最终方案后明确表示批准，下一轮才可进入实施。若用户要求调整方案，更新受影响部分；调整实质改变设计或风险时，重新执行自我复核，再次请求批准。
